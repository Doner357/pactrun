# Documentation writing and maintenance

**Status: Contributor policy for F.**

## Writing baseline

Use the [Google developer documentation style guide](https://developers.google.com/style)
for English prose, headings, lists, procedures, code presentation, and tone.
Selected on 2026-09-27; evaluate upstream revisions deliberately. This reference
does not authorize automatic rewrites of contracts.

Use [Diátaxis](https://diataxis.fr/) for tutorial, how-to, reference, and explanation
roles. Select [Good Docs templates](https://www.thegooddocsproject.dev/templates)
when useful. Product semantics remain owned by Spec.

## Pactrun additions

- Preserve conditions, exceptions, actors, and normative MUST/MUST NOT meanings.
- Use the [glossary](../spec/glossary.md); avoid approximate synonyms for product terms.
- Apply the external guide's directness, tone, and concision rules. Add local phrase
  restrictions only for demonstrated gaps; AI writing habits are not a style baseline.
- Distinguish available behavior, proposals, and historical evidence.
- Describe prerequisites, side effects, expected results, and recovery for procedures.
- Keep essential information in Markdown, accessible without interactive widgets.

## Ownership

| Information | Owner |
| --- | --- |
| Product rules and formats | Owning Spec page |
| Product terminology | Spec glossary |
| Current baseline and work | Next-milestone handoff, linked to evidence |
| Procedures | User and author guides |
| Historical decisions and results | Original decision/delivery records |
| Command spellings | CLI declaration, extracted into generated help |
| Search metadata | Generated catalog and explicit classification exceptions |

Link to changing facts instead of duplicating them. Preserve historical evidence
with clear status and current-owner links. User guides do not carry internal test tables.

## Reader-role completeness

Users and Pack authors should complete their ordinary tasks within their own
documentation categories. Supply field types, allowed values and meanings,
omission/default rules, prerequisites, errors, and worked examples there.
Spec and Development links belong in optional maintainer-source panels, not as
required next steps. Keep task instructions outside those panels. A deliberate
switch from operating to authoring is a role change, not a missing user procedure.
Reader pages use a role-scoped sidebar and keep previous/next pagination in that
role; developer pages retain the complete navigation. Global role selectors stay
available for deliberate context changes.

Plain-language field/task guides are maintained for readers. Advanced reader
references are generated by `website/scripts/reader-references.mjs` from selected
owning contracts; they add no independent requirements. The generator removes
prose requirement-definition labels and verification declarations, preserves the
section anchors, redirects available same-role links, and moves remaining
cross-layer/history sources into an optional panel. JSON schema copies are exact.
Code fences and inline code remain literal, and source links keep their section
fragments. Search excludes optional maintainer citations from task text. In a user
or author audience scope, matching reader guidance precedes Spec for ordinary
queries. Global title relevance is preserved, and exact requirement queries still
prioritize the owning definition. Reader pages provide scoped search links.
The same Markdown views feed HTML and agent text; developer agents still use Spec.

After editing a selected owner, run
`node website/scripts/reader-references.mjs --patch-dir target/reader-reference-patches`
with a fresh output directory, review/apply the emitted patches, and run the
documentation checks. The command only emits patches under `target/`; it does
not silently edit the documents. Tests reject stale views, missing sidebar
entries, required Spec/Development links, and task content hidden in source panels.

## Generated navigation context

HTML, search and agent text share the document-classification model. A reference
can serve several audiences. Review new pages against that model; current
development entries require explicit registration instead of inheriting historical
status. Text context is generated separately from the unchanged Markdown body.
Requirement search targets must pass the rendered-heading check.

Location under `spec/` does not make a reading aid normative. Spec maps, indexes,
and glossaries declare `Status: Informative` and use the `Informative` catalog
role. Retired contract and persistence-schema entry pages use `superseded`
status and remain outside the default Current search scope. Check the HTML
notice, search filters, and agent text together when changing these declarations.

## Editorial and verification checklist

Review reading order as a task dependency graph. Each procedure states its purpose,
prerequisites, expected result, and safe next choices. Installation precedes the
first executable exercise. An exercise that deletes its Instance must not imply
that later tasks can reuse it. Capability-specific tasks state which live Instance
and Pack declarations they need and what an empty listing means.

Keep landing-page links, sidebar order, and guided pagination consistent with
`website/src/lib/reading-order.mjs`. Independent operations, optional tutorials,
lookup references, and historical records are not mandatory next lessons. Return
those readers to task selection or the current baseline. Verify rendered navigation
at both root and project base paths; link existence alone does not establish a
usable reading sequence.

1. Read the applicable contract and this writing baseline before authoring.
2. Update affected reader tasks without inventing behavior.
3. Review specificity, terminology, unnecessary repetition, and unsupported claims.
   When a baseline changes, also review copied summaries, linked reading maps,
   historical slice exclusions, error-owner names, and bootstrap/selector prose.
   A retired heading retained for links does not make its body historical.
   Mark historical scope explicitly and link the current owner. Check that old
   section links still land on the corresponding subject, not merely a valid anchor.
4. Run link, traceability, navigation, generated-content, and example checks.
5. Typecheck and build on the configured remote; inspect desktop/mobile and keyboard use.
6. Record source-qualified results and limits. A prior runtime pass is not a new run.

Automated phrase warnings require editorial judgment. Never weaken safety or
negative requirements to satisfy style. Use [task paths](./reading-paths.md) for
agent context; do not maintain a separate agent version of product contracts.
